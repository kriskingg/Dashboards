# Dashboard System Architecture

This document describes the cross-dashboard topology discovered during ownership mapping. It intentionally separates **generator ownership**, **serving ownership**, and **URL/ingress ownership**.

## Core principle

A dashboard has at least three potentially different owners:

1. **Generator** — code that builds the HTML/data/UI.
2. **Serving layer** — process that serves the generated page over HTTP.
3. **Ingress** — Cloudflare/Tailscale/reverse proxy that exposes the service.

Do not collapse these into one concept.

```text
nifty-options-paper-research/analysis/nifty_multi_shadow/
```

on the active GitHub branch at verification time.

## Serving architecture

The serving layer currently comes from:

```text
/opt/chartink-paper/mcx-paper-research
```

and runs:

```text
python -m mcx_paper.control_server
```

against:

```text
/var/lib/chartink-paper/nifty-multi-shadow/reports
```

This means a page can be **served by MCX infrastructure without being generated by MCX code**.

That distinction was the root cause of the initial ownership confusion and is now an explicit architectural rule.

## Git/repository architecture

A repository name is not an application boundary.

`kriskingg/etf-invest-engine` contains or historically contained multiple responsibilities, including:

- ETF/live execution code;
- market-data/research code;
- NIFTY/BANKNIFTY paper/research implementations;
- deployment definitions;
- historical/research branches.

Therefore every dashboard record must identify the **branch and source path**, not merely the repository.

## Deployment-state architecture

Runtime state and generated reports live outside the Git source tree:

```text
/var/lib/chartink-paper/
```

This is desirable for generated/runtime data, but the current D01 deployment also uses an untracked runtime code copy at the repository top level. That creates deployment drift risk.

Until a dedicated cleanup/migration is designed, treat the current server layout as operational state and do not destructively normalize it.

## Identity rule for future work

When a user refers to a dashboard, identify it using this tuple:

```text
Dashboard ID + URL + server + generator module
```

Example:

```text
D01
URL: triumph.../live_latest.html
Server: chartink-paper
Generator: nifty_multi_shadow/live.py
```

Do not use labels like "ETF dashboard", "paper dashboard", or "the Cloudflare page" alone when multiple systems are in scope.
